STORM: Multi-agent Collaboration
with State Management

STate-ORiented Management for parallel coding agents

Mengyang Liu1,2 Taozhi Chen3 Zhenhua Xu4 Xue Jiang4 Yihong Dong4
1Shanghai Jiao Tong University 2Cortices AI 3Emory University 4Peking University
arXiv PDF Code BibTeX
TL;DR. Giving each coding agent its own git worktree only postpones conflicts to the merge. STORM puts all agents in one shared workspace and accepts a write only if every file the agent has read is still at the version it saw. Stale assumptions are rejected at write time, while the agent still has the context to fix them.

Abstract

Recent advances in multi-agent systems have shown great potential for solving complex tasks. However, when multiple agents edit a shared codebase concurrently, their changes can silently conflict and inconsistent views lead to integration failures. Existing multi-agent systems address this through workspace isolation (e.g., one git worktree per agent), but this defers conflict resolution to a post-hoc merge step where recovery is expensive. In this paper, we propose STORM, i.e., STate-ORiented Management for multi-agent collaboration. Specifically, STORM manages agent states by mediating their interactions with the shared workspace, ensuring that each agent operates on a consistent view of the codebase and that conflicting edits are detected and resolved at write time. We evaluate STORM on Commit0 and PaperBench across multiple LLMs. STORM outperforms the git-worktree-based multi-agent baseline by +18.7 on Commit0-Lite and +1.4 on PaperBench, while achieving comparable or better cost efficiency. Combined with single-agent runs, STORM reaches highest scores of 87.6 and 78.2 on the two benchmarks respectively, suggesting that explicit state management is a more effective foundation for multi-agent collaboration than workspace isolation. STORM can also be plugged into any multi-agent system.

Isolation defers conflicts. It doesn't remove them.

Most parallel coding-agent systems give each agent its own git worktree and merge at the end. That stops agents from overwriting each other while they work, but it also hides every agent's progress from every other agent. Agent A writes a helper that assumes a certain signature. Agent B changes that signature on its own branch. Each branch passes on its own, and the combined program breaks. The failure only shows up at merge time, when both agents have already built on the incompatible design.

Workspace isolation (git worktree)

Each agent works on a private copy. Coupling stays invisible until the manager merges, and by then the conflicting assumptions have spread into dependent edits. Git can merge two textually disjoint edits whose interfaces are semantically incompatible.

State management (STORM)

All agents share one live workspace. An agent sees other agents' latest code as soon as it reads a file. If a file the agent relied on has changed, its write is rejected on the spot, together with what changed, so it can re-plan while its context is still fresh.

Method

An agent doesn't need a frozen snapshot of the whole repository to make a correct edit. It only needs the files it actually read to stay unchanged while it reasons. We call this local state consistency.

Let each file \(f\) carry a monotonically increasing version \(v_f\). As engineer \(a_i\) works, it accumulates a read snapshot \(S_i = \{(g, v_g^{\text{obs}})\}\) of every file it has read and the version it saw. A write by \(a_i\) is valid if and only if

\[\forall\,(g, v_g^{\text{obs}}) \in S_i:\quad v_g^{\text{obs}} = v_g^{\text{cur}}\]

A write can fail in two ways. In a direct conflict, another agent has updated the target file itself. In a stale dependency, some other file the agent read has changed, so its reasoning may rest on outdated context.

1

Write-time conflict control

An optimistic concurrency check, in the style of database OCC. Reads and writes go ahead without blocking, and the check runs only when a write lands. The host-side version comparison costs no extra LLM calls.

2

Reservation on rejection

After a rejection, the agent gets a short reservation on the target file (up to 30 s). This gives it a bounded window to refresh and retry, so two agents can't keep invalidating each other.

3

Intent annotations

Engineers leave short, attributed comments on the code they write. When another agent reads the file, it sees the purpose of the code as well as the code. The convention is injected into each engineer's system prompt automatically.

An intent annotation

# engineer_1: validate numeric inputs before summing
def add(a, b):
    if not isinstance(a, (int, float)):
        raise TypeError("a must be numeric")
    return a + b

The manager is the only agent that commits. Engineers never message each other directly: they coordinate through the shared code and these annotations. STORM sits beneath the agents' file_editor tool, so it can be added to an existing manager–engineer system without changing the agents themselves.

What drives the gain

Component ablations

All variants keep the same manager, four engineers, review loop, and iteration budgets. With the manager workflow held fixed, removing write-time validation drops the score to GitWorktree level.

Other coordination mechanisms

We ported the coordination layers of a shared-memory system (MARBLE) and a CRDT system (CodeCRDT) into the same harness, with the same model and budgets. CRDTs guarantee that text converges, not that the merged program is semantically correct.

Scope and limitations

  • STORM is not a guarantee of semantic correctness. It protects the files an agent has actually read. It can't detect dependencies the agent never looked at, and it can't guarantee that task boundaries are right or that separately accepted edits compose. Most of the remaining failures happen after writes have already passed the version check.
  • Decomposition isn't always worth it. On small, self-contained repositories, a single agent is cheaper and sometimes better (e.g., chardet). A practical deployment can run the single agent first and escalate to STORM only when the repository's tests show it's needed.
  • Only file edits are coordinated. Writes made through the terminal (sed, echo >, scripts) are detected afterwards but can't be rejected in advance, and concurrent shell side effects aren't serialized.
  • Conflicts are tracked per file. Two agents editing different functions in the same file trigger a false conflict, and heavily shared files such as __init__.py become bottlenecks.
  • Intent annotations carry no formal guarantee. They improve results on average, but they can also pass along incomplete or wrong reasoning.
  • The novelty is in the application, not a new concurrency primitive. STORM applies optimistic concurrency control to per-agent context. The contribution is identifying which state has to be validated, and when, for multi-agent software engineering, plus the empirical study behind it.

Questions we were asked

Are the "Combined" numbers an oracle?

No. The single agent and the multi-agent system each produce a complete codebase. For each repository, we keep whichever codebase scores higher on the repository's own test suite. Tests, files, and patches are never mixed between the two submissions. (The arXiv v1 text wrongly describes this as a per-test union.) Selection costs two runs and needs a representative test suite, so we report it separately from the standalone methods.

Is the GitWorktree baseline just a weak git merge?

No. Its manager inspects and integrates the engineers' changes itself, tests the combined repository, and can repair or reassign failed work, using the same prompts, budgets, and reassignment policy as STORM. The difference is when inconsistencies are exposed: after isolated work has piled up, or at the moment of the stale write.

Isn't the gain just more compute?

A controlled study on the same benchmarks and framework (Geng & Neubig, 2026) doubles the single agent's iteration budget from 100 to 200. That changes its score by −1.2 to +5.8 points on Commit0-Lite, far less than the coordination gains. In our ablations, which hold the manager and compute fixed, removing write-time validation alone costs 22.4 Scorew points.

Does rejecting stale writes stop scaling at some point?

Not within the repository sizes in Commit0-Lite. STORM's lead over GitWorktree grows with source-file count, test count, and import density. Acceptance rate does fall as agents are added (81.2% at 4 engineers, 67.1% at 8), and we can't rule out a regime where contention dominates at much larger scales.
