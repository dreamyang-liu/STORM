TL;DR. Giving each coding agent its own git worktree only postpones conflicts to the merge. Stale assumptions are rejected at write time, while the agent still has the context to fix them.

The problem

Isolation defers conflicts. It doesn't remove them.

Most parallel coding-agent systems give each agent its own git worktree and merge at the end. That stops agents from overwriting each other while they work, but it also hides every agent's progress from every other agent. Agent A writes a helper that assumes a certain signature. Agent B changes that signature on its own branch. Each branch passes on its own, and the combined program breaks. The failure only shows up at merge time, when both agents have already built on the incompatible design.

Workspace isolation (git worktree)

Each agent works on a private copy. Coupling stays invisible until the manager merges, and by then the conflicting assumptions have spread into dependent edits. Git can merge two textually disjoint edits whose interfaces are semantically incompatible.

State management (STORM)

All agents share one live workspace. An agent sees other agents' latest code as soon as it reads a file. If a file the agent relied on has changed, its write is rejected on the spot, together with what changed, so it can re-plan while its context is still fresh.

Method

Method

An agent doesn't need a frozen snapshot of the whole repository to make a correct edit. It only needs the files it actually read to stay unchanged while it reasons. We call this local state consistency.

Let each file \(f\) carry a monotonically increasing version \(v_f\). As engineer \(a_i\) works, it accumulates a read snapshot \(S_i = \{(g, v_g^{\text{obs}})\}\) of every file it has read and the version it saw. A write by \(a_i\) is valid if and only if

\[\forall\,(g, v_g^{\text{obs}}) \in S_i:\quad v_g^{\text{obs}} = v_g^{\text{cur}}\]

A write can fail in two ways. In a direct conflict, another agent has updated the target file itself. In a stale dependency, some other file the agent read has changed, so its reasoning may rest on outdated context.

1

Write-time conflict control

An optimistic concurrency check, in the style of database OCC. Reads and writes go ahead without blocking, and the check runs only when a write lands. The host-side version comparison costs no extra LLM calls.

2

Reservation on rejection

After a rejection, the agent gets a short reservation on the target file (up to 30 s). This gives it a bounded window to refresh and retry, so two agents can't keep invalidating each other.

3

Intent annotations

Engineers leave short, attributed comments on the code they write. When another agent reads the file, it sees the purpose of the code as well as the code. The convention is injected into each engineer's system prompt automatically.

What a rejected write returns

# write_file(agent="engineer_2", path="src/core.py", ...)
{
  "success": false,
  "current_version": 9,
  "changed_by": "engineer_1",
  "diff": "--- core.py@v8\n+++ core.py@v9 ...",
  "current_content": "...",
  "stale_files": [
    { "path": "src/utils.py",
      "expected_version": 11, "current_version": 12,
      "changed_by": "engineer_3" }
  ],
  "has_reservation": true
}

Fields mirror WriteResponse in the multiagent_sync module. Values are illustrative.

An intent annotation

# engineer_1: validate numeric inputs before summing
def add(a, b):
    if not isinstance(a, (int, float)):
        raise TypeError("a must be numeric")
    return a + b

The manager is the only agent that commits. Engineers never message each other directly: they coordinate through the shared code and these annotations. STORM sits beneath the agents' file_editor tool, so it can be added to an existing manager–engineer system without changing the agents themselves.

Analysis

Case study: the same coupling, caught at opposite ends

Assignment Coupling-aware assignment Engineer work Focus task Accepted review Rejected review

Paired runs on jinja. Under GitWorktree, the utils.py coupling stays invisible until merge review: the manager rejects the focus diff with a merge-conflict reason, and the same engineer redoes it in the shaded window. Under STORM (restricted to the coupled task set), the manager spots the coupling when it decomposes the task. It puts utils.py and async_utils.py in one assignment and schedules the downstream tasks after it. The focus task passes on its first review.
